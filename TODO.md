- [ ] UX/latency: selecting an entry in [ItemList.tsx](src/components/list/ItemList.tsx) marks it read, but the read state is **slow to propagate to the UI**, and the **sidebar unread count is even slower**. Likely a side effect of moving state reads off the synchronous in-memory `EntryStateCache` onto LanceDB: marking read now goes `.md` write → file watcher → `sync_row` → LanceDB commit (async, via the service queue) → count re-query (`reload` + full unread-set materialization). The old cache was updated *synchronously* by the watcher (instant). Investigate read-after-write latency for user actions now that reads are LanceDB-backed — options: optimistic UI update on mark-read, write-through to LanceDB for user actions (not just `.md`), and/or event-driven count refresh instead of re-query. Ties to the roadmap's open "consistency model" decision and the per-refresh unread-set materialization residual (see [WIP.md](WIP.md), counts).

- [ ] Review the semantic consistency of symbol naming in the Rust layer. Surfaced by the two-phase annotation work: `sync_*` (`sync_row`/`sync_annotations`, [pipeline.rs](crates/xaga-core/src/embeddings/pipeline.rs)) names `.md`→LanceDB-row reconciliation, while `reconcile_*` (`reconcile_atom_file`/`reconcile_feed_entries`, [recovery.rs](crates/xaga-core/src/recovery.rs)) names `.atom`→`.md` filesystem reconciliation. The verbs are split cleanly by layer in *identifiers*, but "reconcile" also leaks into the prose describing the `sync_*` DB operation and into the CLI `recover` doc ("Reconcile LanceDB with the filesystem", [embeddings.rs](crates/xaga-cli/src/cmd/embeddings.rs)) — overloading the word across three senses. Audit the verbs (sync / reconcile / recover / embed / upsert) for one-verb-per-concept and align prose to identifiers. **Also — architectural / abstraction naming:** the consumer/command layer calls `EmbeddingsDb` directly (`unread_ids`/`bookmarked_entries`/`get_entry`/…), binding consumers to LanceDB. The architecture is moving toward **DB-as-cache** — LanceDB is the source-of-read (a *cache*); `.md`/`.atom` are the SoT (the durability invariant — every column reconstructible from the files — is what makes LanceDB a cache, not a second SoT). Consider a thin **read-model / cache abstraction** (a trait the commands depend on, with `EmbeddingsDb` — and historically `EntryStateCache` — as implementations) so the consumer layer depends on "a cache," not on LanceDB specifically. The `is_cache_ready` / `useCacheReady` naming already reflects this abstraction; the rest of the read API does not yet.
